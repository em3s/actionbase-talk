이 모델의 주요 장점은 범용성, 확장성, 쿼리 효율성입니다. 다양한 유저 활동을 일관되게 표현하고, 새로운 활동 유형을 쉽게 추가할 수 있으며, 효율적인 쿼리가 가능합니다. 추가로 이 모델은 최근 AI 분야에서 주목받고 있는 RAG 시스템과 매우 잘 어울립니다. RAG는 LLM이 외부 지식을 참조하여 정확한 정보를 제공할 수 있게 하는 기술입니다. 유저 활동 모델로 저장된 데이터는 누가, 무엇을, 어떻게 했는지와 같은 자연어 형태로 표현할 수 있어 매우 유용하게 사용될 수 있습니다.

다시 유저 활동 모델로 돌아와 설명을 이어가겠습니다. 선물하기 위시 기능을 예로 들어 유저 활동 모델과 실제 데이터를 설명드리겠습니다. 유저 활동 모델은 "유저가 상품을 위시했다"와 같은 구조로 정의됩니다. 이 모델은 실제 데이터의 구조를 결정하는 스키마 역할을 합니다. 모델은 사전에 정의되어 메타스토어에서 관리되며, 개발 단계에서 DDL을 통해 생성됩니다.

실제 데이터는 유저가 위시 기능을 사용할 때 생성되어 HBase에 저장됩니다. 예를 들어 상품 상세 페이지에서 춘식이가 고구마를 위시하면, 액션베이스에 "춘식이가 고구마를 위시했다"는 데이터가 생성됩니다. 여기서 춘식이는 액터, 고구마는 타겟, 위시는 액션이며, 친구 공개는 컨텍스트, 그리고 행동 시간이 타임으로 함께 저장됩니다. HBase에 저장되는 이 실제 데이터는 그래프 구조를 사용하여 인코딩합니다. 춘식이와 고구마는 노드로, 위시는 이를 연결하는 엣지로 표현됩니다.

이 쿼리들은 HBase에 저장된 데이터를 직접 조회하는 방식으로 동작하여 빠른 응답을 보장합니다.

액션베이스의 강력한 기능인 다단계 쿼리에 대해 설명드리겠습니다. 이는 조인이나 그래프 탐색과 유사한 기능을 제공합니다. 예를 들어 춘식이 친구들의 위시 목록을 조회하는 과정을 살펴보겠습니다. 첫째, SCAN 쿼리로 춘식이의 친구 목록을 조회합니다. 둘째, 이 친구 목록을 기반으로 SCAN 쿼리를 다시 사용하여 각 친구의 위시 목록을 조회합니다. 두 번째 SCAN은 첫 번째 쿼리 결과를 참조합니다. 다단계 쿼리의 강점은 각 단계의 GET, COUNT, SCAN을 자유롭게 조합할 수 있다는 점입니다.

다음 슬라이드에서는 다단계 쿼리의 실제 예제와 그 동작 방식을 살펴보겠습니다. 이제 실제 예제인 "춘식이 친구들이 위시한 상품 중 가장 인기 있는 탑 5를 조회하는 쿼리"를 예로 들어, 액션베이스가 어떻게 일을 처리하는지 설명드리겠습니다. 먼저 앞서 설명드린 대로 춘식이 친구들의 위시 목록을 조회합니다. 그다음 액션베이스 메모리에 로드된 데이터를 참조하는 SQL 쿼리를 실행하여 최종 결과를 생성합니다. 각 쿼리 중간 및 최종 결과는 자체 구현한 데이터프레임으로 처리되며, JSON 형식으로 클라이언트에 제공됩니다. 응답에는 요청한 쿼리의 이름, 스키마 정보, 그리고 실제 데이터가 포함됩니다. 이를 통해 액션베이스에 한 번 저장된 유저 활동 데이터는 다양한 비즈니스에 활용될 수 있습니다.

## 기술적 특징

이제 액션베이스의 주요 기술적 특징에 대해 설명드리겠습니다. BASE 모델, 동시성 수행 제어 방식, 그리고 일관성 모델, 멱등성에 대해 다루겠습니다.

데이터베이스 시스템은 두 가지 주요 접근 방식이 있습니다. 첫째, ACID 모델로 원자성, 일관성, 고립성, 지속성을 보장하여 즉시 일관성과 정확성을 중시합니다. 둘째, BASE 모델로 기본 가용성, 소프트 상태, 최종 일관성을 특징으로 하며 높은 성능과 수평 확장을 제공합니다.

액션베이스는 대규모 데이터를 효율적으로 처리하기 위해 BASE 모델을 선택했습니다. 이는 대규모 실시간 처리에 적합하며 급격한 트래픽 증가에도 유연하게 대응할 수 있기 때문입니다.

다음은 동시성 수행 제어에 대해 설명드리겠습니다. 분산 환경에서 여러 클라이언트가 동시에 같은 데이터에 접근할 때 충돌로 인한 데이터 불일치가 발생할 수 있습니다. 예를 들어 유저가 상품을 위시했다 취소했다 빠르게 반복할 때, 네트워크 지연으로 서버에 도착하는 순서가 뒤바뀔 수 있습니다. 이러한 불일치를 방지하기 위해 동시성 제어가 필요합니다.

동시성 수행 제어 방식은 크게 두 가지가 있습니다. 비관적 동시성 수행 제어(PCC)와 낙관적 동시성 수행 제어(OCC). PCC는 락을 획득하고 데이터 처리가 완료된 후 락을 해제하는 방식입니다. 반면 OCC는 트랜잭션 종료 시점에 충돌을 검사하는 방식으로 수행됩니다.

액션베이스는 비관적 동시성 수행 제어 방식인 PCC를 채택했습니다. 실제 분산 환경에서 효과적인 동시성 수행 제어를 위해 분산 락을 구현하여 사용했고, 데이터 쓰기 작업에만 락을 획득하도록 했습니다. PCC를 선택한 주된 이유는 데이터 쓰기 시 부가적인 인덱스와 카운터 갱신이 필요했기 때문입니다. 예를 들어 유저가 상품을 위시할 때 위시 수와 인덱스도 함께 업데이트해야 합니다. PCC는 이런 복합 연산을 안전하고 간편하게 처리할 수 있어 우리 시스템에 적합합니다.

분산 시스템에서 주로 두 가지 일관성 모델이 있습니다. Eventual Consistency(최종 일관성)와 Strong Consistency(즉시 일관성)입니다. 여기서는 Strong Consistency를 즉시 일관성이라 표현했습니다. 액션베이스는 이 두 가지 모델을 모두 제공하고 있습니다.

액션베이스는 기본적으로 최종 일관성을 구현하여 시스템의 성능과 확장성을 최적화했습니다. 이는 데이터 업데이트가 즉시 모든 노드에 반영되지 않지만, 시간이 지나면 모든 데이터가 일관된 상태가 되는 방식을 말합니다.

즉시 일관성은 앞서 설명드린 PCC를 통해 구현되었습니다. 동일 세션 내에서 쓰기 작업이 완료된 후 읽기를 수행하도록 하여 즉시 일관성을 보장하며, 이를 통해 유저는 자신의 최근 활동의 최신 상태를 즉시 확인할 수도 있습니다. 실제 서비스에서는 최근 본 상품 리스트는 최종 일관성으로, 위시나 찜은 즉시 일관성을 사용하도록 설정하여 연동하였습니다.

멱등성은 동일한 연산을 여러 번 수행해도 결과가 달라지지 않는 특성을 말합니다. 액션베이스에서는 각 데이터의 버전 정보를 포함시키고 조건부 업데이트를 통해 멱등성을 구현하였습니다. 이를 통해 네트워크 오류 등으로 인한 중복 요청을 안전하게 처리할 수 있습니다.

여기서는 이벤트 순서와 시스템 처리 순서가 다른 상황을 보여줍니다. 예를 들어 나중에 발생한 T3 이벤트가 T2보다 먼저 처리되어도 최종적으로는 올바른 데이터 상태에 도달합니다. 또한 이벤트가 중복 처리되더라도 시스템은 동일한 최종 상태를 유지하여 멱등성을 보장합니다. 이러한 구현을 통해 액션베이스는 이벤트 처리 순서의 변동이나 중복 처리와 같은 다양한 상황에서도 안정적으로 운영되고 있습니다.

내부적으로 데이터 상태 관리 시스템을 구현하여 데이터 변화를 효과적으로 처리하고 있습니다. 데이터는 Initial, Active, Inactive 상태로 관리되며, 삽입, 삭제, 갱신 요청 시 버전 정보를 고려하여 적절한 상태로 전이가 됩니다. 이를 통해 모든 가능한 데이터 상태와 전이 과정을 빈틈없이 고려한 효율적이고 안정적인 로직을 구현하였습니다.

## 데이터 파이프라인

이제 액션베이스의 스트리밍/배치 데이터 파이프라인에 대해 설명드리겠습니다. 먼저 앞서 데이터 쓰기 흐름에서 설명드린 사전 기록 로그(WAL)와 데이터 변경 캡처(CDC)를 다루고, 스냅샷 및 마이그레이션 프로세스에 대해 말씀드리겠습니다.

먼저 사전 기록 로그(WAL)에 대해 말씀드리겠습니다. WAL은 데이터의 변경 사항을 실제로 적용하기 전에 로그에 먼저 기록하는 기법입니다. 이 로그에는 변경 요청 정보가 들어 있으며, 실시간 데이터 마이그레이션에서 매우 중요한 역할을 합니다.

다음으로 CDC(변경 데이터 캡처)에 대해 설명드리겠습니다. CDC는 데이터의 변경된 사항을 저장하는 프로세스입니다. 이 로그에는 데이터 변경 요청과 더불어 before에는 저장소에 저장된 이전 상태, after에는 요청을 처리한 다음 상태를 가지고 있으며, after는 다음에 설명드릴 스냅샷 생성에 중요한 역할을 합니다.

액션베이스에서는 WAL과 CDC 모두 카프카를 통해 처리하고 있습니다. 카프카를 사용함으로써 높은 처리량과 신뢰성을 확보할 수 있었습니다. 이러한 기술을 통해 시스템 장애에 효과적으로 대비할 수 있게 되었고, 다른 시스템과의 데이터 동기화도 매우 효율적으로 수행할 수 있게 되었습니다.

이제 스냅샷과 마이그레이션 프로세스에 대해 설명드리겠습니다. 스냅샷은 특정 시점의 전체 데이터 상태를 의미합니다. 액션베이스에서는 주로 데이터 마이그레이션, 백업, 분석, 시스템 복구에 활용되고 있습니다. 스냅샷 생성은 카프카로 유입된 CDC 데이터의 최신 상태를 유지하는 방식으로 구현하였습니다. 기존 데이터가 MySQL, MongoDB 등에 저장되어 있었다면 덤프 후 초기 스냅샷을 생성했습니다. 현재는 스파크 스트리밍과 배치로 구현했으며, 향후 Iceberg 등의 기술을 고려 중입니다.

마이그레이션은 이 스냅샷을 활용해 수행됩니다. 먼저 1일 단위로 생성된 전일자 스냅샷을 HBase에 벌크 로드합니다. 그 후 카프카의 WAL을 전일 11시 50분부터 재생하여 최신 상태로 동기화합니다. 이는 0시 경계 구간의 데이터 누락을 방지하기 위함입니다. 멱등성으로 중복 적용에 대한 걱정 없이 안전하게 진행할 수 있습니다.

여기서 벌크 로드는 HBase의 내부 저장 형식인 HFile을 직접 생성하고 복사하는 방식으로 동작합니다. 이는 마치 MySQL 내부 데이터를 직접 만들어 복사한 후 MySQL을 실행하는 것과 유사합니다. 이 방식은 개별 레코드를 삽입하거나 여러 레코드를 묶어서 처리하는 것보다 훨씬 효율적입니다. 이 방식을 활용함으로써 기존 시스템에서 액션베이스로 이전이나 HBase 클러스터 이전과 같은 대규모 마이그레이션 작업도 수시간 내에 완료할 수 있게 되었습니다.

## 시스템 구성 및 안정성

다음으로 시스템 구성 및 안정성 확보 방안을 설명드리겠습니다. 먼저 코드 구조를 살펴보겠습니다. 크게 네 가지 모듈이 존재하고, 앱과 코어는 Kotlin, 스트리밍과 배치는 Scala, 그리고 데이터 정의는 코어 레이어와 배치 레이어의 공유를 위해 Java로 구현되었습니다. 각 모듈에는 유닛/통합 테스트가 작성되어 견고하게 관리되고 있습니다.

액션베이스의 시스템 구성에 대해 설명드리겠습니다. 먼저 클라이언트의 접근은 GSLB를 통해 이루어지며, 이를 통해 트래픽이 세 개의 IDC로 구성된 쿠버네티스 클러스터로 분산됩니다. 액션베이스 애플리케이션은 이 쿠버네티스 클러스터 위에서 실행되고 있습니다. 유저 활동 모델은 메타스토어에서 관리되고 있으며, 실제 유저 활동 데이터는 HBase에 저장됩니다. 그리고 WAL과 CDC는 카프카로 전송됩니다. 안정성과 성능을 보장하기 위해 섀도우 테스트와 모니터링을 실행하고 있으며, 모든 시스템 자원은 다중화되어 있어 안정적으로 작동할 수 있습니다.

테스트 관련해서 더 자세히 설명드리겠습니다. 먼저 안정성 확보 방안인 시나리오 테스트에 대해 설명드리겠습니다. 액션베이스와 서비스 연동 시 비즈니스에 대한 상세한 엔드투엔드 시나리오를 작성하고 예상 결과도 함께 정의했습니다. 이렇게 하면 코드 변경 시 유닛/통합 테스트뿐만 아니라 시나리오 테스트도 함께 수행할 수 있습니다. 이를 통해 새로운 기능이나 변경 사항이 기존 기능에 영향을 미치지 않는지 확인할 수 있습니다.

다음으로 섀도우 테스트에 대해 말씀드리겠습니다. 섀도우 테스트는 실제 유저 요청을 신규 버전으로 미러링하여 테스트하는 것입니다. 이를 통해 배포 전에 잠재적인 문제를 실 트래픽 기반으로 파악할 수 있습니다. 슬라이드를 보시면 트래픽이 인그레스를 통해 현재 버전과 최신 버전으로 동시에 전달되는 구조를 확인할 수 있습니다. 이렇게 하면 실제 서비스에 영향을 주지 않으면서도 새로운 기능을 실시간 환경에서 테스트할 수 있어, 성능과 안정성을 정확하게 평가할 수 있습니다. 결과적으로 유닛/통합/시나리오 테스트에서 발견하지 못한 문제들을 사전에 발견해 배포 리스크를 크게 줄일 수 있습니다. 최근 카카오 릴리즈 프로세스가 강화되었고, 이에 발맞춰 액션베이스는 배포 전 최소 하루 이상의 섀도우 테스트를 진행하고 있습니다.

## 마무리 및 향후 계획

마무리 및 향후 계획을 말씀드리겠습니다. 액션베이스는 대규모 실시간 유저 활동 데이터를 서빙하는 시스템으로, 선물하기 위시, 쇼핑하기 찜, 다양한 프로모션에 성공적으로 적용되었습니다. BASE 모델을 구현하여 안정적이고 견고하게 시스템을 관리하고 있습니다. 주요 키워드로는 유저 활동 모델, BASE 모델, 최종 일관성, 멱등성, 사전 기록 로그(WAL), 변경 데이터 캡처(CDC), 섀도우 테스트가 있습니다. 앞으로의 계획은 시스템을 지속 가능하게 만드는 것과 함께, 시대 흐름에 맞춰 LLM과의 연동을 시도해보는 것입니다.

마지막으로 이 자리를 빌어 감사의 말씀을 전합니다. 우선 카카오 여러 인프라 조직에 감사의 말씀을 전합니다. 지원해 주신 덕분에 액션베이스를 만들고 안정적으로 운영할 수 있었습니다. 또한 선물하기, 쇼핑하기, 쇼핑탭 등 서비스 조직에 감사드립니다. 신뢰를 가지고 적용해 주셨고 여러 피드백을 해 주셔서 더욱 발전할 수 있었습니다. 마지막으로 방향성을 믿어준 우리 커머스 플랫폼 조직의 리더와 멤버들 덕분에 여기까지 올 수 있었습니다. 다시 한번 진심으로 감사드립니다. 앞으로도 잘 만들어봤으면 좋겠습니다. 이것으로 액션베이스에 대한 소개를 마치겠습니다. 경청해 주셔서 감사합니다.
